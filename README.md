# 视频猎手 · 使用说明

飞牛 fnOS 应用：填入网址，扫描页面收集视频，批量下载到 NAS 共享目录。

> **这个仓库**只放业务源码与构建脚本，不含第三方运行时（Chromium / yt-dlp / curl_cffi / ffmpeg 加起来约 600MB），也放不下编译好的 fpk（233/251MB，超过 GitHub 100MB 单文件限制）。要二次构建，按 [`scripts/fetch_deps.sh`](scripts/fetch_deps.sh) 和文末「附录：源码包与二次构建」补齐 `app/vendor/` 后打包；只想用的话直接去下载页拿 fpk。

---

- 应用标识：`videohunter`
- 依赖：`python312`（应用中心会自动装）
- 安装包（按机型二选一）：

| 文件 | 适用机型 | 体积 |
|---|---|---|
| `videohunter_1.4.0_x86.fpk` | Intel / AMD 处理器（绝大多数机型） | 233MB |
| `videohunter_1.4.0_arm.fpk` | ARM64 处理器（如 ARM 版 F 系列、N 系列） | 251MB |

> 比 1.3.1 大约多了 40MB：多带了独立 ffmpeg（HLS 合并、音视频合流靠它，fnOS 精简系统多数没装）和 Chrome 指纹库。

不确定自己用的是哪种？SSH 登录后执行：

```bash
uname -m
```

输出 `x86_64` 用 x86 包，输出 `aarch64` 用 arm 包。装错架构时应用中心会直接拒绝安装，不会装坏系统。

---

## 一、安装

1. 打开 fnOS **应用中心** → 右上角 **手动安装**
2. 上传与你机型匹配的那个 fpk（x86 或 arm）
3. 安装向导里勾选「安装完成后立即启动」
4. 装完在桌面出现「视频猎手」图标，点开即用

> 首次启动需要初始化下载队列，约 2–5 秒。若桌面打开白屏，等几秒刷新。

命令行安装（可选）：

```bash
# x86 机型
appcenter-cli install-fpk videohunter_1.4.0_x86.fpk

# ARM 机型
appcenter-cli install-fpk videohunter_1.4.0_arm.fpk
```

## 二、使用

### 1. 扫描

在输入框粘贴网址，点「扫描」。支持三类目标：

| 目标 | 例子 | 走哪条路 |
|---|---|---|
| 平台视频页/播放列表 | B 站合集、YouTube 频道、Vimeo 专辑 | yt-dlp 直接展开，几秒出结果 |
| 普通站点的视频列表页 | 自建站的 `/videos` 列表 | 静态解析 + 同域爬取 |
| 靠 JS 渲染的播放页 | 网课、自建播放器 | 无头浏览器渲染 + 网络请求嗅探 |

扫描过程会显示当前阶段（识别页面 → 抓取 → 解析 → 渲染 → 爬取 → 校验），右侧有两个按钮：

| 按钮 | 效果 |
|---|---|
| **暂停 / 继续** | 挂起扫描（不再发新请求，已扫到的结果原地保留），点「继续」接着跑 |
| **停止** | 立刻收尾，把停止前已扫到的视频**汇总成结果列表并默认全选**，直接点「下载选中」就能下，不用重扫 |

站点太大、或者扫到一半发现只想要前几集时，点「停止」比等它跑完划算——停止不是白干，已经拿到的都能下。

打开应用后先看顶部那行字：显示 `浏览器渲染已启用 · 145.0.7632.6` 这类带版本号的状态，说明内核正常工作；显示「不可用」时把鼠标移上去看原因。

### 2. 挑选与下载

- 结果列表显示标题、时长、分辨率、上传者，以及「已确认 / 直链」标记
- 「已确认」= 引擎解析出了完整元信息，成功率最高
- 「直链」= 直接抓到的 mp4/m3u8 地址，能下但没有元信息
- 勾选后点「下载选中」，队列在下方实时显示进度、速度、剩余时间
- 队列右上角「清理已完成」清掉已完成/失败的任务（只清列表，不动已下载的文件）

### 3. 成品位置

默认保存到应用自己的数据目录：

```
/vol1/@appshare/videohunter/data/视频猎手/视频标题 [id].mp4
```

在 fnOS「文件」→「应用数据」里能看到（`@appshare` 是应用数据的挂载点，不在普通共享文件夹里）。

**想放到共享文件夹**（方便 Jellyfin / Emby 索引、或手机直接访问）：打开设置，点「下载目录」输入框——1.2.0 会把 NAS 上的共享文件夹列成候选，选中即可；也可以手填绝对路径，例如：

```
/vol1/1000/我的共享/视频猎手
```

保存后新任务就写到那里，界面底部会实时显示当前生效的路径。

## 三、设置

点右上角「设置」：

| 项 | 说明 | 建议 |
|---|---|---|
| 下载目录 | 留空则用共享目录/视频猎手 | 想放别的盘就填绝对路径 |
| 同时下载数 | 1–8 | 家用 2–3 足够，太多会互相抢带宽 |
| 画质 | 最佳 / 1080p / 720p / 480p | 想省空间选 480p |
| 请求间隔 | 扫描时的页间隔（毫秒） | 站点敏感就调大到 800–1000 |
| 单次最多校验条数 | 每次扫描最多验真多少条 | 大批量站点调到 200 |
| Cookie 文件 | Netscape 格式 cookie 路径 | 需要登录的站点才用 |
| 代理 | http://ip:port | 访问境外站点时用 |
| TLS 指纹伪装 | 默认开启 | 模拟 Chrome 的 TLS 指纹。有些站浏览器能开、程序访问就 403 或只给空壳页面，靠它绕过；副作用极小，不建议关 |

### 需要登录的站点

1. 浏览器装扩展导出 `cookies.txt`（Netscape 格式）
2. 上传到 NAS，例如 `/vol1/1000/共享文件夹/cookies.txt`
3. 设置里填这个路径，保存

## 四、技术实现

```
videohunter.fpk
├── app/
│   ├── videohunter.py        HTTP 服务（标准库，监听 unix socket）
│   ├── core/
│   │   ├── crawler.py        四层扫描：引擎探测 → 静态解析 → 浏览器 → 深爬
│   │   ├── engine.py         yt-dlp 子进程封装，解析进度
│   │   ├── browser.py        Playwright 渲染 + 网络媒体嗅探
│   │   ├── tasks.py          下载队列、并发闸门、状态持久化
│   │   └── settings.py       配置与目录解析
│   ├── vendor/               内置运行时（目标机无需联网装依赖）
│   │   ├── yt_dlp/           下载引擎
│   │   ├── impersonate/      curl_cffi，负责 Chrome TLS 指纹伪装
│   │   ├── bin/ffmpeg        静态 ffmpeg 7.0.2（HLS 合并/合流）
│   │   ├── playwright/      浏览器驱动
│   │   └── browsers/
│   │       ├── chromium-*/   内核
│   │       └── lib/          内核依赖的 79 个系统库（自带，不依赖 fnOS）
│   └── ui/                   前端单页（原生 JS）
├── cmd/                      9 个生命周期脚本
├── config/                   privilege（低权用户）+ resource（共享目录）
└── manifest
```

几个关键点：

- **零安装依赖**：yt-dlp、Playwright、Chromium 全部内置，目标机断网也能跑。
- **自带系统库**：Chromium 需要的 79 个库（libnss3、libgbm、libatk、libcups…）也打进包内，启动时用 `LD_LIBRARY_PATH` 优先加载。fnOS 是精简系统，这一步是为了不要求你先去 `apt install` 一堆桌面库。
- **网关前缀自处理**：fnOS 统一网关不剥 `/app/videohunter` 前缀，应用自己剥。
- **断点续传 + 队列持久化**：服务重启后，没下完的任务自动重新排队接着下。
- **停止即干净**：按进程组 kill，不会留下 yt-dlp 子进程占带宽。
- **下载中断可重试**：失败任务单独重试，不用整个重来。

## 五、已知限制

| 情况 | 表现 | 说明 |
|---|---|---|
| DRM 加密（Netflix、部分付费课） | 无法下载 | 不做破解，也不建议 |
| 强反爬站点 | 扫描为空或 403 | 试 cookie + 代理；仍不行需针对性适配 |
| 视频藏在 blob: 地址 | 扫不到 | 浏览器已尽力，可手动从 F12 抓 m3u8 后粘贴 |
| 视频在跨域 iframe 里、且要交互才加载 | 可能扫不到 | 1.3.0 会尝试点开播放控件；仍不行就用 iframe 的地址扫一次 |
| 站点限制无头浏览器 | 扫不到 | 填 cookie 或换真实浏览器抓 m3u8 |
| 首次安装体积 | 191–213MB | 主要是 Chromium 内核，属于一次性成本 |

> ARM 版说明：ARM 包内置的是 Playwright 官方 aarch64 内核（Chromium 153），与 x86 包的 145 属不同构建线，功能一致。若某个站点在 ARM 机型上扫不出内容，先用「关掉浏览器渲染」试一次，再排查系统库。

## 六、排错

**桌面打开空白**
服务没起来。SSH 进 NAS 看日志：

```bash
tail -50 /var/apps/videohunter/var/app.log
bash /var/apps/videohunter/cmd/main status   # 0=运行中，3=已停止
bash /var/apps/videohunter/cmd/main restart
```

**扫描直接报「这个网址在当前网络下打不开」**

这说明域名在你所在的网络里被阻断了，和扫描器本身无关。1.3.1 会在扫描前 1 秒做一次体检，直接告诉你卡在哪：

```
扫描失败：这个网址在当前网络下打不开：系统 DNS 解析到 173.252.248.244，
公共 DNS 是 66.220.149.32，两者不一致（DNS 被污染）；这类域名在国内网络下必须走代理
```

```
扫描失败：这个网址在当前网络下打不开：TCP 能连上，但 TLS 握手被直接重置（域名被阻断）；
这种和站点无关，只能用代理访问
```

两种判定分别对应 DNS 污染和 SNI 阻断，共同点是：**不加代理无论换什么参数都扫不到**。

处理办法只有一个——在「设置 → 代理」里填一个**能访问该站**的代理：

| 代理类型 | 填法 |
|---|---|
| HTTP / HTTPS 代理 | `http://192.168.1.2:7890` |
| SOCKS5 | `socks5://192.168.1.2:1080` |
| 带账号密码 | `http://user:pass@192.168.1.2:7890` |

1.3.1 起，这个代理对**扫描抓取、无头浏览器渲染、下载**三层全部生效（此前只有下载走代理，所以设了也没用）。

**重要**：代理本身得在能访问该站的线路上。把代理指向同一台 NAS 或同一路由器的同一条宽带，域名照样被阻断——代理必须落在有境外线路的机器上（路由器上的透明代理、另一台挂了 VPN 的设备，或商业代理）。

**扫描不到 / 只扫到几个**
1.3.0 起扫描过程会写日志，先看它扫到了哪一层：

```bash
grep "\[scan\]" /var/apps/videohunter/var/app.log | tail -20
```

```
[scan] 静态解析 https://站点/list → 直链 0 个，HTML 412 KB
[scan] 渲染 https://站点/list → 嗅探 1 条媒体，iframe 0 个，新增 1
[scan] 完成 https://站点/list → 12 条（已验真 0），页面 8，耗时 31.5s，警告：…
```

对照着处理：

| 日志现象 | 含义 | 处理 |
|---|---|---|
| 静态解析 0 个，页面也很小（<20KB） | 返回的是壳页/验证页 | 填 cookie；换用「列表页」而非首页 |
| 渲染那行显示「内核不可用，跳过渲染」 | 只有静态解析在工作 | 见下面「浏览器渲染不可用」 |
| 渲染成功但「嗅探 0 条」 | 播放器要点了才加载，或被反爬识别 | 换详情页地址再扫；必要时填 cookie/代理 |
| 页面数远小于站点实际页数 | 爬取深度/页数上限到了 | 设置里把「爬取深度」调到 3，或多扫几个列表页 |
| 结果里有页面地址而不是直链 | 引擎只认出了视频页 | 直接勾选下载也行，下载时会再解析一次 |

另外两条通用办法：
- 「请求间隔」调到 100ms，扫描更快，但被限流的站要反过来调大
- 扫描时先用列表页/专辑页，别用首页

**文件名后面为什么有一串字符**
`视频标题 [id-3f2a1b].mp4` 里的 `-3f2a1b` 是下载地址的指纹。不同地址撞同名时（CDN 上大量 `index.m3u8`）不会互相覆盖；同一地址重复下载仍会命中同一个文件，断点续传照旧。嫌长可以下载后自己改名，不影响播放。

**顶部显示「浏览器渲染不可用」**
鼠标悬停那行灰字，会显示具体原因。能显示版本（如 `浏览器渲染已启用 · 145.0.7632.6`）就说明内核是好的。若仍不可用：

1.2.1 起，内核自检改在**后台**进行：刚装完或刚重启时可能短暂显示「正在检测浏览器内核…」，几秒到一分钟内会出结果（慢盘机器首次启动要读 100MB+ 的内核文件，属正常）。结论也会写进 `app.log`：

```
[20:53:31] 浏览器内核：可用（145.0.7632.6）
[20:53:31] 浏览器内核：不可用（降级静态解析）— 内核启动超时（20 秒无响应）
```

想立刻重测：设置 → 底部「重新检测内核」。

| 提示 | 含义 | 处理 |
|---|---|---|
| 缺少动态库 xxx.so | 系统缺库 | 1.2.0 会自动改用包内库；若仍失败，把这句话发我 |
| 内核启动超时（20 秒无响应） | 内核在这台机器上起不来（常见于 ARM + 精简系统） | 点「重新检测内核」再试；仍失败就先用静态解析，把日志发我 |
| 内核启动异常 / 退出码非 0 | 二进制与架构不匹配 | 确认装的是对应架构的包 |
| 包内未找到 Chromium | 安装包不完整 | 重新安装 |

不影响下载：不可用时自动降级为「静态解析」，普通 `<video>` 页面照样能扫。

**下载报 403 / 需要登录**
1.3.0 起，扫描到的直链会自动带上下载来源页（Referer），多数防盗链站点已能直接下。仍 403 时填 cookie 文件路径后重试；有代理的再填代理。

**提示「目录里已有同名文件，已跳过」**
说明该地址之前下载过。要去掉重下，先删掉旧文件；想保留两份就改个名再下。

**进度卡在 0%**
多半是 m3u8 分片地址被防盗链。填 cookie 或代理重试。

**磁盘满了**
设置里换下载目录，或清理已完成任务。

| 版本 | 变更 |
|---|---|

| **1.2.0** | 修复浏览器内核被误判为不可用（版本号识别）；补齐 Python 3.12 的 greenlet 扩展（旧包在 fnOS 的 python312 上渲染模块加载失败）；内置依赖库改为**按需启用**（库齐全时用系统库，避免渲染进程崩溃）；顶部状态显示内核版本；下载目录可从共享文件夹列表选择 |

## 附录：源码包与二次构建

`videohunter-src.zip` 是全部业务源码（36 个文件，约 53KB），不含第三方运行时。**两个架构包共用同一份业务代码，差异只在 `manifest` 的 `platform` 和 `vendor/` 下的二进制。**

补依赖后即可重新构建：

```bash
# 1. 解包
unzip videohunter-src.zip && cd pack

# 2. 补下载引擎（纯 Python，与架构无关）
pip download yt-dlp --no-deps --only-binary :all: -d /tmp/w
unzip /tmp/w/yt_dlp-*.whl -d app/vendor

# 3. 补浏览器驱动（下面的 manylinux2014_aarch64 换成 x86_64 即为 x86 版）
pip download playwright==1.58.0 pyee==13.0.1 --no-deps --only-binary :all: \
    --platform manylinux2014_aarch64 --python-version 3.11 -d /tmp/w2
# greenlet 要 cp311 与 cp312 两个 ABI（fnOS 的 python312 只能用 cp312 那份）
for v in 3.11 3.12; do
  pip download greenlet --no-deps --only-binary :all: \
      --platform manylinux2014_aarch64 --python-version $v -d /tmp/w2
done
cd app/vendor && for f in /tmp/w2/*.whl; do unzip -qo "$f"; done && cd ../..
# 两个 .so 都在 greenlet/ 下即可，Python 会按自身版本选

# 4. 放浏览器内核（目录名与架构必须对应）
#    ARM:  chromium-1243/chrome-linux-arm64/chrome
#    x86:  chromium-1208/chrome-linux64/chrome  （Chrome for Testing 145）
#    目录下需有空的 INSTALLATION_COMPLETE 与 DEPENDENCIES_VALIDATED 标记文件
#    查找规则见 settings.py 的 _find_chrome()：遍历 browsers/ 下
#    chrome-linux64 / chrome-linux / chrome-linux-arm64 三个目录名，
#    找到可执行文件即经 executable_path 显式传入，不依赖 Playwright 默认的 revision 匹配

# 5. 收齐内核依赖库（脚本从 Debian bookworm 索引解析闭包）
#    输出到 vendor/browsers/lib。注意：运行时只在 ldd 报缺库时才启用，
#    库齐全的机器仍用系统库，否则版本交叉会让渲染进程崩溃
python3 collect_libs.py <chrome路径> /tmp/<arch>-sysroot app/vendor/browsers/lib <triple>

# 6. 按需设置 manifest 的 platform（x86 / arm），然后构建
bash <fnos-fpk技能>/scripts/build_fpk.sh ./pack 1.2.0
```

关键约束：**内核目录名必须是 `chrome-linux64` 或 `chrome-linux-arm64`**（见 `settings.py::_find_chrome`）；代码用 `executable_path` 显式指定内核，所以 revision 与 Playwright 默认版本不一致也能跑，实测 x86 用 1208、ARM 用 1243 都正常。
